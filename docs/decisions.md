# 项目决策记录：一句话生成 H5 小游戏平台（带 AI 试玩）

> 记录时间：2026-11-08
> 用途：项目设计依据 + 面试讲解备忘。每条都写了"选了什么 / 还考虑过什么 / 为什么 / 面试怎么讲"。
> 参考项目：[kagayatsuki/Freedom_Code](https://github.com/kagayatsuki/Freedom_Code)（Spring Boot + LangChain4j + Vue3 的前端代码生成平台）

---

## 0. 一句话介绍（电梯演讲）

> 用户输入一句话（比如"躲陨石的太空飞船游戏"），平台用 **Claude 写代码、Codex 审查**，再由 **AI 试玩员在 Docker 沙箱里真的去玩**：读游戏状态、模拟操作、截图评估，发现问题就自动修复，最后把能玩的游戏连同完整的"进化过程回放"发布到在线作品展。

---

## 1. 项目定位

| 项 | 决定 |
|---|---|
| 目的 | 写进简历，投 **AI 全栈开发（Java 方向）** |
| 截止时间 | 无 |
| 选题 | 一句话生成 H5 小游戏 + AI 试玩 |
| 用户 | 只有我自己（本地工具），不对外开放生成 |

**还考虑过的方向**：草图/截图 → 网页（带视觉比对自检）、需求 → Spring Boot + Vue 全栈后台。

**为什么选小游戏**：
- 演示冲击力最强，面试时现场就能玩
- "AI 试玩测试"是很少见的点，能和普通"AI 生成网页"项目拉开差距
- 和参考项目技术栈相近，但选题不同，不会被认为是照搬

**面试怎么讲**：普通代码生成平台的"成功"标准只是"编译通过"。我想解决的是**生成的东西到底能不能用**，游戏是最需要"真的去玩一下"才能验证的场景。

---

## 2. 技术栈

- 后端：Java 21 + Spring Boot（编排、沙箱调度、事件流）
- 前端：Vue3（本地生成平台 + 作品展）
- 生成的游戏：**Vite 多文件工程**（可 npm 引入 Phaser 等游戏库）
- 模型：**本地 Claude Code CLI + Codex CLI，使用个人订阅**
- 沙箱：Docker
- 版本管理：每个游戏项目一个 git 仓库
- 作品展：GitHub Pages（纯静态）

## 3. 关键决策

### 决策 1：生成的游戏用 Vite 多文件工程

- **还考虑过**：原生 Canvas 单文件（最稳，但工程感弱）、直接用 Phaser 等引擎（不走构建）
- **为什么**：三点都想要：
  1. 体现工程化（模块拆分、构建流程）
  2. 能 npm 引入游戏库（Phaser、Matter.js、Howler 等）
  3. 多轮修改更精准：只改 `player.js` / `enemy.js`，不用每次重写一个大文件
- **代价**：npm install / build 慢 → 用**预热容器池**解决（见决策 6）
- **面试怎么讲**：单文件生成更稳，但没法演示"精准修改单个模块"，也没法用游戏引擎。我选了更难的路，用容器池预热依赖来抵消速度问题。

### 决策 2：模型接入用订阅 CLI，而不是 API

- **还考虑过**：Java 自写 Agent 循环 + 按量付费 API（DeepSeek/Qwen）；双引擎可切换
- **为什么**：用已有的 Claude / Codex 订阅，不额外花钱，生成质量高
- **已知代价（要心里有数）**：
  - Agent 内部的推理/工具循环在 CLI 里，不是我写的 → 面试会被问"不就是调了个命令行吗"，所以 Java 层要有足够的自研深度（见决策 3、4）
  - 订阅只限个人使用 → 平台**只在本地运行，不对外开放生成**，作品展只展示结果（见决策 9）
  - 订阅有速率限制 → 编排层要处理限速与断点续跑
- **面试怎么讲**：我把"写代码"这种通用能力交给最强的现成 Agent，把精力放在它们做不了的事上：多 Agent 协作、结果验证、沙箱隔离、过程可追溯。另外我做了引擎抽象层，换成 API 版只需加一个适配器。

### 决策 3：Java 层的三条技术主线（都要做，分阶段）

1. **多 Agent 编排**：Claude 写、Codex 审、试玩员提 bug，循环到通过
2. **AI 试玩系统**：探针协议 + Playwright + 截图评估
3. **沙箱与任务调度**：Docker 预热容器池、任务队列、SSE 实时日志

**第一版优先做：多 Agent 编排**，另外两条先做最简单的版本。

### 决策 4：编排层重点打磨三件事（应对"套壳"质疑）

1. **可恢复的状态机**：每一步的状态、输入、输出都落库；服务重启、容器崩溃、CLI 限速后都能从断点续跑；支持取消和重试。这份数据**同时也是作品展回放的数据源**。
2. **CLI 输出解析与流式转发**：解析 claude/codex 的 stream-json 输出，统一成自己的事件模型，通过 SSE 实时推给前端；统计 token、耗时、工具调用。
3. **引擎抽象层**：统一的 `AgentEngine` 接口，Claude/Codex 只是两个实现。以后接 API 或别的 CLI，只需加一个适配器。

- **面试怎么讲**：调 CLI 只是一行代码，难的是让一个可能跑十几分钟、中途会限速、会崩的多 Agent 流程**可靠、可观测、可恢复**。

### 决策 5：Claude 写、Codex 审，意见分级 + 轮数上限

- **分工**：Claude 是编码员；Codex 只读代码，输出**结构化审查意见（JSON）**，不改文件
- **还考虑过**：加一个策划 Agent 先写设计文档；Claude 和 Codex 各写一版，择优
- **冲突处理**：
  - 审查意见分**阻塞级 / 建议级**，只有阻塞级必须修
  - 最多 **3 轮**审查-修复
  - 超过上限时以**试玩结果为准**：试玩能过就放行，未解决的意见记录下来，进回放
- **审查范围**：只审本轮 git diff（更快、更省额度、意见更聚焦）
- **面试怎么讲**：两个 Agent 可能互相拉扯、无限循环，所以我设计了分级和上限，并且用"客观的试玩结果"作为最终仲裁，而不是让某个模型说了算。

### 决策 6：沙箱 = Docker 预热容器池，CLI 也跑在容器里

- **CLI 位置**：claude/codex CLI 也放进容器，登录凭证**只读挂载**；宿主机上只跑 Java 后端
  - 原因：CLI 会自己写文件、执行命令。参考项目 Freedom_Code 直接在宿主机跑 npm，这是它最大的安全问题
- **容器策略**：**预热容器池**：后台常驻几个已启动的容器（镜像里预装 Node、CLI、Playwright、Vite+Phaser 模板依赖），任务来了直接领一个，用完销毁并补充
  - 还考虑过：每个任务新起一个容器（简单但慢）、每个项目一个长期容器（容器越积越多）
- **网络**：**完全开放**（最简单，依赖文件隔离 + 资源限制）
  - 还考虑过：白名单代理（只放行模型 API 和 npm 源），更安全但配置复杂。**以后可升级，面试时可作为"已知取舍 + 改进方向"来讲**
- **面试怎么讲**：池化设计（预热、借出、归还/销毁、补充、健康检查）+ 隔离（文件系统、凭证只读、CPU/内存限制）。并且能主动说出网络没做隔离这个取舍，以及升级方案。

### 决策 7：AI 试玩怎么做

- **状态读取：约定探针协议 + 截图**
  - 生成的游戏必须在 `window.__GAME_PROBE__` 上暴露统一接口：当前状态、分数、实体列表、可用操作、事件日志
  - Playwright 读探针做精确断言；截图交给视觉模型评估观感
  - **探针协议是我的原创设计，是面试重点**
- **怎么玩：脚本测试 + AI 自由玩**
  - 先跑固定脚本做硬性检查（随机按键、不操作等死、连点重开），不消耗模型额度
  - 再让 Claude 写一段 Playwright 玩法脚本去"认真玩"，按验收标准断言
  - 还考虑过：AI 逐帧决策（最像人，但太慢太费额度）
- **"好不好玩"的作用：只报告，不卡门**
  - 硬性检查（不报错、能操作、能结束/重开）不过 → 必须修
  - 好玩度按固定维度打分 + 给建议（与需求契合度、难度、视觉、反馈感），写进回放，**由我决定要不要继续改**
  - 原因：好不好玩是主观的，模型打分不稳定，不适合当自动卡点
- **面试怎么讲**：把"测一个游戏"拆成可确定的部分（探针 + 脚本断言）和不确定的部分（视觉模型打分），前者卡门，后者只做参考。这是对 LLM 不确定性的工程化处理。

### 决策 8：多轮修改

- **版本管理**：每个项目一个 **git 仓库**，每轮通过后自动 commit
  - 能看 diff、一键回退；回放里的代码 diff 直接从 git 取
  - 数据库只存元数据（轮次、commit hash、审查结果、试玩分数）
- **修改方式**：**文字 + 在画面上圈选**：预览时可暂停游戏，在截图上框一块区域写意见，截图和框选一起交给 Claude
- **面试怎么讲**：不重复造版本管理的轮子；圈选修改是多模态交互，比纯文字描述更精准。

### 决策 9：作品展与回放（GitHub Pages）

- **访客能做什么**：玩游戏 + 看生成过程（**不能现场生成**，因为订阅不能给别人用，Pages 也没有后端）
- **发布方式**：**手动挑选 + 一键发布**：本地平台点"发布到作品展"，后端导出游戏 build 产物 + 回放 JSON + 截图到展示仓库，git push 后由 GitHub Actions 自动部署 Pages
- **回放形式**：**像看直播一样自动播放**：按真实顺序加速重放整个生成过程，文件一个个出现、审查意见弹出、试玩截图出现
- GitHub 仓库 README 放作品展链接
- **面试怎么讲**：编排状态机里的每一步本来就要落库，回放只是把这份数据导出成静态 JSON 再做一个播放器，一份数据两个用途。

### 决策 7 实施补充（2026-11-16，P5a）：AI 试玩员的门槛怎么定

- **流程**：每个 Run 的第一次试玩前，Claude（试玩员角色）读代码写一段试玩脚本（`export default async function play(t)`）；平台在硬性检查通过后运行它。脚本只能通过平台给的 API 操作游戏，**断言结果由平台记录，不让模型自己报告"通过了"**。最后 Claude（评委角色）看截图打分。
- **门槛**：硬性检查 + AI 断言都要过；脚本自己出错或一个断言都没有 → 算"无结论"，**不会冤枉一个好游戏**；试玩修复轮数用完时，以客观的硬性检查为准放行（避免模型写错的断言把好游戏拖成失败）。评委打分只报告、不卡门。
- **控制成本**：脚本每个 Run 只写一次、修复后复用；评委只给最终通过的版本打分。
- **还考虑过**：让模型自己玩并汇报结果（不可信）；AI 断言只报告不卡门（发现了问题却不修，没意义）。
- **面试怎么讲（真实踩坑）**：第一次用真实引擎生成贪吃蛇就失败了——不是游戏坏了，是我的硬性检查判错：贪吃蛇本来就在自己动，按方向键只是改方向，而检查只看"按键后有没有新东西在动"。Claude 被一个误判拖着修了两轮还是失败。修法是识别"方向变化"（用每次采样位移的中位数判断转向，避免穿屏这类跳变被当成转向），并且某个键在当前状态合理无效时（正在向右走时按右、或者按反方向），先用别的键换个状态再试。补了贪吃蛇样本做回归，原来"自己会动但按键失灵"的样本仍然判失败。**教训：验证器本身也会出错，要用真实数据跑过才算数。**

### 整体审查（2026-11-16，P4–P5b）

补做了 P4 当时推迟的整体审查：独立的审查 Agent 只读审查 P4 到 P5b 的全部改动，报告 11 条，逐条核实后全部修复。值得面试讲的几条：

- **验证器的假阳性**：方向变化检测没有对照组，球自己反弹、跳跃到最高点下落都会被当成"按键有效"。改成先连续观察两段不按键的窗口，自己会转向的物体不算数；去掉"开始/停止移动"规则（对按格子走的贪吃蛇会乱跳）；游戏结束不算按键有效。残余风险：恰好在按键窗口里自己反弹，仍可能放过失灵的键——下一层 AI 实玩会真的按键断言，所以是**分层防御**而不是单点完美。
- **"AI 试玩不会冤枉好游戏"只对引擎错误成立**：Docker 失败、没配引擎等运行时异常会把硬性检查已通过的游戏判失败。改成除取消以外的任何失败都算"无结论"或跳过。
- **不可信脚本的隔离**：AI 写的试玩脚本原来和试玩器跑在同一个进程，理论上能伪造报告、用死循环卡死试玩器。改成放进 Worker 线程，只能通过消息调用平台给的 API，报告由试玩器在结束 Worker 后打印；补了"伪造报告""同步死循环"两个集成测试。
- 其余：取消的步骤在事件流里补发结束事件、AI 写的文本发事件前脱敏、先导出预览再让评委打分、看旧版本时轮询新版本状态、页面加载请求防乱序、截图只显示在构建的最后一轮试玩上、窗口缩放时保留画面。

### 决策 8 实施补充（2026-11-16，P5c）：圈选修改怎么落地

- **截图怎么拿**：游戏跑在不透明源的沙箱 iframe 里，平台页面读不到它的画布（这是 P3 有意做的安全隔离，不能为了截图拆掉）。做法是预览页注入一个很小的"桥"脚本（和高清补丁一起注入）：平台用 postMessage 发一个带随机数的截图请求，桥只回复父页面，把最大的画布 `toDataURL` 回传；平台只接受**来自这个 iframe、随机数对得上**的回复。截图在下一帧动画回调里读，所以没开 `preserveDrawingBuffer` 的 WebGL 画布一般也能截到；截不到（比如跨域图片污染了画布）就提示改用文字。
- **坐标用什么单位**：框选在前端存成 0–1 的比例，后端再换算成**游戏代码里的画布像素**（桥回传的是画布逻辑尺寸，即游戏代码看到的 `canvas.width/height`，高清补丁不会改变它），提示词里写"框 1：x 120–360，y 40–120，画布 480×320"。Claude 既能看图，也能直接在代码里找对应坐标。
- **图片怎么给 Claude**：前端把编号红框画到截图上（最长边压到 1280），后端校验 PNG 文件头和 4 MB 上限，存到工作区目录**旁边**（不进任何游戏仓库，不会被同步进沙箱，也不会被提交）。每次写代码/修复之前把图片写进容器的 `/tmp/playforge/marked.png`，提示词让 Claude 先用 Read 打开；容器重启续跑时会重新写入。图片写不进去时只给坐标，不影响生成。
- **审查和试玩不变**：圈选只影响 Claude 收到的需求；Codex 审查和 AI 试玩照常跑。
- **故事里能看到**：这一版的"修改需求"下面显示带框的截图（`GET /api/runs/{id}/markup.png`）。
- **真实验收**：在接金币游戏上框住篮子，写"框 1 的篮子改成带提手的藤编篮子，宽度加大一半"。Claude 先打开截图再改 `render.js`，Codex 审查通过；AI 试玩员针对"篮子加宽后贴墙"写了断言，第一次没过，Claude 按报告修好，第二次 7 项全过，用时 2 分 8 秒。

### 决策 10：不做的东西（刻意裁剪）

- **不做**登录、配额、限流、支付：单用户本地工具，精力放在 AI 能力上
- **面试怎么讲**：这些我知道怎么做（JWT、Redis 令牌桶），但这个项目的核心价值不在这里，所以刻意砍掉了。

## 6. 面试高频问题速答

- **"不就是调了个 CLI 吗？"** → 调用是一行代码；难点是可恢复状态机、多 Agent 冲突仲裁、试玩验证、容器池隔离。并且有引擎抽象，可换成 API。
- **"你怎么判断生成结果是对的？"** → 三层：Codex 静态审查 → 探针协议 + 脚本的确定性断言 → 视觉模型主观评分（只报告不卡门）。
- **"两个 Agent 意见冲突怎么办？"** → 分级 + 3 轮上限 + 以试玩结果为最终仲裁。
- **"安全怎么做？"** → CLI 和构建都在容器里，凭证只读挂载，资源限制；网络开放是已知取舍，可升级白名单代理。对比参考项目在宿主机直接跑 npm 的问题。
- **"为什么用多文件工程，不用单文件？"** → 工程化、能用游戏库、多轮修改能精准改单个模块；速度问题用预热容器池解决。
- **"跟 Freedom_Code 有什么区别？"** → 选题不同（游戏 vs 网页）；验证标准不同（真的去玩 vs 编译通过）；多 Agent 交叉审查；容器隔离；过程可回放。
